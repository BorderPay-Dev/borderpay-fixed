# Transfer webhook ownership correction

The reported EURC transfer `d4d6d19b-b48f-4649-8a6e-95a4dab8b4fc` succeeded at Bridge. Customer-provided SQL results show a consumed, unexpired PIN/TOTP payment authorization and local `sca_used` evidence. Its four signed transfer webhooks failed with `upsert_bridge_transfer_projection ... bt_owner_xor`.

Bridge's Transfer schema uses `on_behalf_of` for the customer being served: https://apidocs.bridge.xyz/api-reference/transfers/get-a-transfer. The worker read only legacy customer fields and called the projection RPC with two null owner fields before handling missing ownership. The source schema's constraint named `bt_owner_xor` rejects that ownerless row; the fix does not loosen the database constraint.

The worker now accepts the canonical field, retains legacy customer identifiers, rejects conflicting or malformed identifiers, and requires a unique locally mapped owner before transfer or partner-status writes. Customer endpoint fields cannot override the canonical transfer customer. Both ownership queries must succeed; an error in one cannot silently select an owner from the other. Tests invoke the actual transfer handler for business/individual mappings, legacy responses, counterparties, missing/ambiguous identities and failed lookups. The handler only projects the already-executed payment and does not create a new transfer or consume SCA again. The existing database trigger retains the transaction's SCA metadata on mirror updates.

The failed event records still require recovery after deployment. Inspect their actual `on_behalf_of` field, current queue attempts and the deployed retry RPC before redriving them. Use the supported queue lifecycle operations; do not disable ownership constraints, fabricate owner IDs, delete audit events, or clear the original SCA authorization. Historical events must not be replayed out of order so that an older pending state overwrites the processed payment. No production event replay has been performed by this release.
